# Frontend Testing Strategy

## Goals

- Catch regressions in browser-independent logic (URL codec, models,
  algorithms) with fast unit tests.
- Verify that components render the right data from the GraphQL API.
- Run fully without a live backend: every GraphQL request is answered by MSW
  from recorded fixtures.
- Fast feedback: the full suite runs in seconds.

## Tech Stack

| Concern              | Tool                                                |
| -------------------- | --------------------------------------------------- |
| Test runner          | Vitest 4, configured in `vite.config.ts` (`test`)   |
| Browser              | Playwright provider, Chromium (headless by default) |
| React rendering      | `vitest-browser-react`                              |
| Request interception | MSW 2 (`setupWorker`, `graphql.*`)                  |
| Fixture data         | Recorded JSON files (`src/testing/fixtures/`)       |

## Test Projects

Tests are split into two Vitest projects (`test.projects` in `vite.config.ts`),
selected by filename:

| Project   | Files                    | Environment                               | For                                                   |
| --------- | ------------------------ | ----------------------------------------- | ----------------------------------------------------- |
| `unit`    | `*.test.{ts,tsx}`        | `node`                                    | Browser-independent code (logic, algorithms) — no DOM |
| `browser` | `*.browsertest.{ts,tsx}` | Vitest browser mode (Playwright/Chromium) | Components, rendering, MSW-backed integration         |

- `pnpm test` — run everything once (headless).
- `pnpm test:watch` — watch mode, both projects.
- `pnpm test:unit` / `pnpm test:browser` — a single project in watch mode.
- `pnpm test:headed` — browser tests with a **visible** browser window
  (`HG_HEADED=true`). Browser tests are headless by default so CI, the sandbox,
  and other display-less environments work without extra flags.
- `pnpm test:browser:update` — update `toMatchScreenshot` baselines (`-u`).

### Screenshot artifacts

`toMatchScreenshot` baselines live in `__screenshots__/` next to the test file
and are committed (reference data). Failure screenshots are redirected to a
throwaway `__artifacts__/` folder (via `screenshotDirectory` +
`resolveScreenshotPath` in the browser project), so the two never mix.
`__artifacts__` and `.vitest-attachments` are gitignored; `__screenshots__` is
not. There are currently no `toMatchScreenshot` assertions — the separation is
in place for when visual baselines are added.

## Test Structure

Tests sit next to the code they test. Shared infrastructure:

```
src/
  testing/
    fixtures/               recorded GraphQL fixture JSONs (do not edit by hand)
    msw/
      handlers.ts           MSW graphql.query handlers backed by the fixtures
      worker.ts             setupWorker export
    public/
      mockServiceWorker.js  generated by msw init (do not edit)
    render.tsx              renderWithQueryClient / renderWithRouter helpers
    setup.ts                global MSW lifecycle; unhandled requests fail the test
```

## Fixtures

Fixtures are **recorded** from a running Hierograph server serving a
deterministic example project, and committed. They are never written or edited
by hand: if a test needs data the recording doesn't contain, grow the example
project and re-record. Recording must be deterministic — volatile values such
as paths, times and process ids are normalised before writing, so re-recording
unchanged data produces identical files.

The recorder and the first fixtures come with the start screen, which is the
first component that queries the server.

## Adding New Tests

1. **Pure logic** (browser-independent) → add a `*.test.ts` (runs in the `unit`
   project, `node` environment). No DOM available.
2. **Component** → add a `*.browsertest.tsx` (runs in the `browser` project)
   and render with `renderWithQueryClient`, or `renderWithRouter` when the
   component reads or writes search params. MSW intercepts all requests
   automatically (setup in `src/testing/setup.ts`).
3. **New GraphQL operation** → add a `graphql.query` handler to
   `src/testing/msw/handlers.ts` and record the operation.

## Known Constraints

- **Canvas coordinate system**: headless Chromium uses `devicePixelRatio=1`, so
  CSS pixels equal physical pixels; click coordinates in canvas tests are CSS
  pixel values.
- **optimizeDeps**: packages used by browser tests must be listed in the
  browser project's `optimizeDeps.include` (in `vite.config.ts`) to avoid the
  optimizer discovering them mid-run and loading a second React instance.
- **Browser tests run sequentially** (`fileParallelism: false` on the browser
  project in `vite.config.ts`). Vitest's default file-parallelism launches one
  Chromium instance per test file simultaneously; on memory-constrained hosts
  (containers, CI, a sandbox with ~2GB free) that OOM-crashes mid-run with
  `Browser connection was closed` / `[birpc] rpc is closed` on a random file —
  not a test failure, a resource limit. The provider also passes
  `--disable-dev-shm-usage` (routes Chromium's shared memory off the 64MB
  container `/dev/shm` to `/tmp`); this flag belongs on the Playwright
  **provider** (`playwright({ launchOptions })`), not on a browser instance,
  where Vitest silently ignores it.
